### Identity: record, answer key and listing rows

- One record is one answer file. Its answer key is `pq:ls:<session>:<stem>` from its own `file_url`
  (`pq_answer_key`, `20261028130000_pq_admission_links.sql:14-19`; `pqAnswerKey`, `_shared/suppliedText.ts:58-60`).
- The listing is `desk_rows` of `national / Parliamentary Question Database`: 8,000 rows, `row_key` "1" to "8000",
  pinned to their question (F266 spec §10). Rows carry **no** `document_key`; the key is computed from
  `row.source_url` wherever identity is checked (F266 spec §9).
- One answer serves one row per asking member. In v1.1: 8,000 links, 8,000 distinct `row_key`s, 6,840 distinct link
  keys, every link's key equal to its record's. **704 answer keys are shared by 1,864 rows** (up to 11 rows on one
  answer). In the shipped listing (`public/data/embedded_csv/national_question_database.json`), the rows on each shared
  key agree on subject, ministry, date, question type, house and URL, and no member appears twice. Every link's row
  carries the record's `file_url` as `source_url` (8,000 of 8,000).
- No question (session, type, number) has two answer files, in the pack or the listing. 127 session and number pairs
  exist as both starred and unstarred questions, so the type is part of the identity.
- Records reach answers only through `record_document_links`. The resolver's key join is for `bill:` and
  `law-record:` keys only (`20261110180000_record_resolver_shared_bill_keys.sql`), and a question row's attachment key
  is its `desk-record:` pointer (`src/lib/deskRows.js:93-107`: no `bill_number`, so no bill key). F314, F315 and F316
  are key joins that question records never use.

## Problem

The runner and admission take only screened records, and no screen writes a review for answers. The owner's F266
rules exist only in disabled Colab tooling, so any answer the bulk path loads, now or from a later pack, would need them
re-applied by hand. And the F314 lesson applies: a key several listing rows share must be found and handled, not
assumed unique.

## Expected outcome

1. A question screen (`--screen national-pq`) that applies every F266 rule, the text-per-page check and admission's own
   refusals, and writes a review only from checks that ran.
2. On v1.1 it reproduces the owner's result exactly: 6,683 held `already_live`, the same 157 keys held for the reasons
   in the table above, 0 screened.
3. Before any NTER load, the screen and admission agree on a local copy: what the screen passes, admission admits, with
   exactly the listing links NTER already holds for those answers.

`listing_rows` holds:

- `no_live_row`: no live row carries the URL (admission's `no_desk_row`);
- `link_row_missing`: a link's `row_key` is not among those rows;
- `listing_rows_differ`: a live row carries the URL but the record does not link it. Admission would link it without
  the owner's member check (lines 302-317), so the screen holds it. The remainder cohort's live check required the same
  equality (`remainder-cohort/README.md`, "pack row sets equal the live rows");
- `listing_disagrees` (detail: the field names): any of those rows differs from the citation on URL, subject, answer
  date, question type, ministry, house, or its member is not in `asked_by`. Text fields are compared in both forms,
  the owner's (`norm`, letters a-z and digits only) and admission's (`pq_norm`, Unicode letters and digits, runs of
  anything else as one space), so the screen never passes what admission refuses.

Everything admission checks is pre-checked, so it shows as a screen hold, not a refusal that counts against the
refusal cap. The screen is stricter than admission where the owner's rules are (member, question type, row set, text
checks), never looser.

### Live reads (interface change)

Both are read-only and run as the developer's login. They do not call `pq_answer_key` (granted to `service_role`
only); they write its rule out, as the resolver does for `bill_norm`.

- `deskRows` takes `sourceUrls?: string[]` beside `documentKeys` (now optional; at least one list given): rows of the
  tier and feature whose `row->>'source_url'` is in the list.
- `documents` takes `pqAnswers?: string[]` (answer keys): national documents whose `file_url` is the key's URL with or
  without `?source=pqals`, or question documents whose `metadata->>'document_key_suggested'` is the key or whose
  `source_path` file name is `<session>_<stem>.pdf`, or national documents whose URL names the same session, type and
  number under another stem. `LiveDocument` gains `answer_key?: string | null`: the key the document matched.
- `screen.ts` takes `--service <name>` (default `nter-accept`), so the rehearsal can read a local copy. The receipt
  already records the database and server.

### Near-duplicates (`screens/pq_near_duplicate.ts`)

The owner's rule, on the same shingles (lowercased `\w+` words, 5 at a time, crc32):

- held `near_duplicate` when exact containment is at least 0.90 and the pair ties (same session, type and number, or
  the same answer date), or at least 0.97 with at least 300 shingles on both sides; set sizes within 3 times;
- held `contained_same_date` when the sizes are more than 3 times apart, the dates are equal, the smaller has at least
  50 shingles and at least 0.80 of it is inside the larger.

Differences from the Python, all toward holding more, never less:

- The decision is the same exact containment, but candidates are found without MinHash (its random constants cannot be
  reproduced in TypeScript): every same-date or same-question pair is compared exactly, and other pairs are compared
  when a deterministic sketch (the 64 smallest shingle hashes) shares at least half. The parity run (T4) must find every
  pair the Python found and lists any extra.
- It compares a record not already live with every record in the input set, live ones included (the set holds every
  live answer's pack text, as the remainder cohort's registry did), and holds every not-live member of a pair, whatever
  the order. The `already_live` check shares its set of live keys with this check, as `listing_row` shares `matched` in
  the Bills screen.
- Within the input set only. A later pack's answers must also be compared with v1.1's: that needs a reference input
  (question 5).
