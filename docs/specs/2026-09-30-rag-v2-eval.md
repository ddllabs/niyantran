# Spec: retrieval evaluation set and harness (`eval`)

> **Status: Living — draft for owner approval (2026-09-30).** It becomes
> Normative once approved. Module `eval` of
> `docs/specs/2026-09-30-rag-v2-capability-map.md`. The evidence is
> `docs/research/2026-09-30-rag-v2-investigation.md` §3. Revision 2 folds in a
> fresh-context adversarial review of revision 1: 16 findings, all accepted
> (see "Review record").

## Objective

Give every later retrieval change something to be measured against. The
evaluation set is a fixed list of questions, each with a known answer location
in today's corpus. The harness sends those questions to `match_documents` and
reports how often the right document and passage come back, and how fast. Its
first run records **today's baseline**. `retrieval-scope` must then show it is
"no worse", as defined below, *before* that change is deployed.

It is used by the supervisor and task agents, who run it before and after a
retrieval change, and by the owner, who reads the report.

**What it is not.** It is not a copy of `research-chat`'s retrieval path. The
chat agent calls the same RPC as the signed-in user (`caller()`, under RLS
and the `authenticated` statement timeout), with a query the model rewrote,
and possibly with a `desk_tier` (`supabase/functions/research-chat/index.ts:
348-354`). The harness calls it as `service_role`: no RLS, a 300 s timeout
(`20260921000010_service_role_timeout.sql:13`), and the question as written.
So the harness measures retrieval quality. It does not measure the agent's
query rewriting, or the timeout that users hit (see "Latency").

## Current state (read and executed 2026-09-30)

- **No evaluation asset exists.** The F22 figures (recall@40 0.9875; 161 ms
  mean on the server) appear only in prose (`20260929120100:5-16`,
  `docs/agents/coordination.md`), and the queries were never committed. F22
  measured index fidelity, approximate against exact search with chunk
  embeddings as queries, not whether a question finds its answer.
- **The corpus** is 2,338 documents and 54,219 chunks (executed, a
  read-only query):

  | desk_feature (exact value in `documents`) | Docs | Chunks |
  | --- | --- | --- |
  | Bill Passage Probability Index | 1,743 | 42,025 |
  | Regulatory Body Watch (RBI SEBI TRAI CCI) | 506 | 11,040 |
  | Parliamentary Question Database | 82 | 1,108 |
  | Industry Updates (Ministry Data) | 6 | 40 |
  | Budget Utilisation & Schemes | 1 | 6 |

  `_shared/deskCatalog.json` spells the regulatory module
  "(RBI/SEBI/TRAI/CCI)". The harness uses the exact `documents` value.
- **`match_documents`** (`20260929120100:27-105`) returns `id` (the chunk
  id), `document_id`, `content`, `similarity`, `chunk_index`,
  `source_kind`, `page_number`, `char_from`, `char_to`, `title`,
  `file_name`, `file_url`, `desk_tier` and `desk_feature`. It does **not**
  return `chunk_hash`, `document_key` or `metadata`.
  - The unscoped branch ranks by halfvec distance but returns
    full-precision similarity, so row order is the ranking.
  - The scoped branch is exact with a per-document quota of
    `ceil(match_count / n)`.
- **Chunk identity** (ADR 0004): `chunk_hash` is SHA-256 over
  `chunker_version ‖ unit_key ‖ normalised text`. It is not the `text_hash`
  that `retrieval.ts:68` computes. Chunk ids are stable until a re-chunk
  changes boundaries.
- **Embeddings** are `openai/text-embedding-3-small`, 1536 dimensions,
  through OpenRouter (`_shared/embed.ts`). Provider embeddings are not
  guaranteed to be bit-identical from one call to the next.
- **Chat models.** The live default is `google/gemini-3.8-flash` (executed,
  `ai_models.is_default`). The migrations still seed older models: live data
  has moved past them.
- **Environment.** `.env.local` has `VITE_SUPABASE_URL` and
  `SUPABASE_SECRET_KEY`. It has no `SUPABASE_URL` and no
  `OPENROUTER_API_KEY`.
- **Conventions:**
  - Scripts run under `vite-node --config vitest.config.js`.
  - `vite-node` strips the script path, so arguments come after `--`. The
    pattern is `scriptArgs()` in `scripts/load-desk-rows.mjs:158-167`.
  - Vitest collects only `src/**/*.test.{js,jsx}`.
  - Node `fetch` works only outside the sandbox.
  - AGENTS.md requires both test suites for any change under `src/lib/`.

## Expected outcome

### 1. The question set: `eval/retrieval/questions.v1.jsonl` (committed, frozen)

Each line is one JSON object:

| Field | Meaning |
| --- | --- |
| `id` | `q-0001` … |
| `question` | the question text |
| `desk_feature` | the exact `documents.desk_feature` value |
| `gold_document_ids` | array; one entry for generated questions |
| `gold_chunk_id` | the chunk the question was written from (null for owner questions without one) |
| `gold_chunk_hash`, `gold_content_sha256` | drift checks only; never used to score |
| `gold_char_from`, `gold_char_to` | the gold span, for the report |
| `document_key` | looked up once, at build time, from `documents.metadata->>'document_key'` |
| `distractor_ids` | four documents from the same feature, frozen at build time; empty when the feature has fewer than five documents |
| `ambiguous` | true when a near-identical passage exists in another document (see step 4 below) |
| `source` | `generated` or `owner` |
| `generator_model` | the model that wrote the question |
| `created_at` | build time |

**Stored vectors.** `eval/retrieval/questions.v1.vectors.json` is committed.
It holds one 1536-float vector per question, about 2 MB, plus a SHA-256 of
each vector. Committing the query vectors removes embedding noise from every
comparison. These are vectors of questions, not of the corpus.

### 2. The harness

- **Code:**
  - runner `scripts/eval-retrieval.mjs`, using the `scriptArgs()` pattern;
  - logic in `src/lib/retrievalEval.js`.
- **Environment.** It reads `SUPABASE_URL`, falling back to
  `VITE_SUPABASE_URL`, and `SUPABASE_SECRET_KEY` (which must be
  `sb_secret_…`). It needs `OPENROUTER_API_KEY` only when a vector is missing.
- **Corpus fingerprint.** Before any query, it reads and records:
  - document and chunk counts;
  - the latest `indexed_at`;
  - the `match_documents` migration version, i.e. the newest applied
    migration;
  - for every gold chunk, whether it still exists with the same
    `chunk_hash`.

  If any gold chunk is missing or changed, it **aborts** with a list, and
  reports no scores.
- **Output.** It writes `eval/retrieval/results/<timestamp>.json`, holding
  every question's ranked result ids (not their content) plus the metrics,
  and a Markdown report.

### 3. The baseline report

`docs/research/<run-date>-retrieval-baseline.md`, with its JSON committed
beside it.

### Modes

| Mode | Call | Notes |
| --- | --- | --- |
| `broad` | unscoped, `match_count` 40 | Whole corpus. |
| `focused` | `p_document_ids = gold_document_ids` | Today's scoped branch, unchanged by `retrieval-scope`. It is measured so that a later change to the scoped SQL cannot regress unnoticed. |
| `focused-multi` | gold plus the frozen `distractor_ids` | Skipped when there are no distractors. The quota is `ceil(40/5) = 8` per document, so chunk hit@k for k > 8 is capped. The report states this. |
| `feature` | added by `retrieval-scope`: the question's own `desk_feature` | This is the harness supplying the right feature. In production the model has to choose it, and that is tested in `retrieval-scope`, not here. |

### Metrics

Overall and per feature. Ranking is **the row order** returned by the RPC,
never a re-sort by `similarity`.

- **Document hit@k** (k = 5, 10, 40): any returned chunk has
  `document_id ∈ gold_document_ids`. A second figure, "same-key hit", also
  accepts a document with the same `document_key` (bill-key collisions,
  open-work P14). The key of each returned document is fetched once per run.
- **Chunk hit@k** (k = 5, 10, 40): the returned chunk `id` equals
  `gold_chunk_id`. There is no overlap rule. Because the fingerprint aborts
  on any drifted gold chunk, an exact id match is always valid.
- **MRR@40**, at document level and at chunk level.
- **Per-question outcome.** For each question, the rank of its first
  gold-document hit and of its gold chunk hit, or "miss". Comparisons use this,
  not only totals (see "No worse").
- **`ambiguous` questions** are scored and shown, but kept out of the
  pass/fail bars.
- **Latency.** Each mode's calls are shuffled with a fixed seed, and
  preceded by 5 unscored warm-up calls. Reported per mode:
  - p50 and p95 of the RPC round trip from the laptop;
  - the same figures for a network baseline: `select id from documents limit
    1` through PostgREST;
  - the mean response size in bytes, because 40 chunk contents dominate the
    transfer.
- **Cost.** Embedding tokens and dollars: zero when every stored vector is
  present.

### How the set is built (`scripts/build-eval-set.mjs`, logic in `src/lib/evalSet.js`)

1. **Candidate chunks.** A paged read, 1,000 rows at a time. Candidates are
   chunks whose document has `indexed_at` set and whose `embedding` is not
   null. A candidate is excluded if its content:
   - is shorter than 300 characters;
   - is mostly table (at least 60% of lines satisfy the chunker's own
     table-row rule, `isTableRow` in `_shared/chunking.ts`);
   - is only an enacting formula or signature block.
2. **Sampling that doesn't favour long documents.**
   - Order the documents of each feature by `md5(id::text)`, computed in
     JavaScript.
   - Take one candidate chunk per document, the first by `md5(chunk id)`,
     cycling through the documents until the feature's target is met.
   - Targets: Bills 80, Regulatory 60, Parliamentary Questions 40, Industry
     12, Budget 3. That makes 195.
   - Industry has 6 documents, so it takes 2 chunks each. Budget's single
     document gives 3.
3. **Generation.**
   - The live default chat model, recorded per line, writes one question per
     chunk.
   - The question must be one a researcher would ask, answered by the passage,
     without quoting it, and without naming the file or any id.
   - **The 5-word leakage check.** Text is normalised (NFKC, lowercase,
     punctuation removed, split on whitespace; this also works for Devanagari).
     The question is rejected if it shares any 5-token sequence with the
     passage.
   - A rejected question is regenerated once. If that also fails, the
     candidate is skipped and the next one in the same order is used.
4. **Ambiguity.** For each gold chunk, its own stored embedding is sent to
   `match_documents` (unscoped, 5 results). If a chunk from another document
   has similarity ≥ 0.98, the question is marked `ambiguous`. Near-duplicates
   such as reprinted clauses would otherwise count correct answers as wrong.
5. **An independent judge.**
   - A model from a different vendor than the generator (for example
     `anthropic/claude-sonnet-5`, which is on the allowlist) grades every
     question against the rubric: answerable from the passage, specific, not
     trivial.
   - Failing questions are replaced, as in step 3.
   - Then the supervisor hand-reviews 40 random questions. At least 38 must
     pass, or the prompt is fixed and the set regenerated.
   - The owner reviews 20 with the same rubric. At least 18 must pass.
6. **Owner questions (optional).** The owner may add up to 20 real research
   questions, each with the document or documents that answer it. They are
   reported separately and never count toward the bars.
7. **Frozen.** Once committed, the set is not changed. A new set is `v2`.

## Code style

- **Runners** follow `scripts/load-desk-rows.mjs`: they load `.env.local`,
  check the key prefix, use `scriptArgs()`, and put all logic in an importable
  module.
- **Logic** consists of pure functions, taking the client and `fetch` as
  parameters, so tests can pass in fakes.
- **Secrets** are never logged.
- **Reads** from PostgREST are paged, 1,000 rows at a time.
- **Retries** are bounded, on 429 and 5xx only.

## Testing strategy

- **Vitest, for everything that decides a score:**
  - hit@k boundaries (a gold hit at rank k and at rank k+1);
  - MRR;
  - the same-key variant;
  - that ranking uses row order;
  - the fingerprint abort on a missing or changed gold chunk;
  - the leakage check, including Devanagari;
  - the sampling order and per-document cycling;
  - question-line validation;
  - the `focused-multi` skip.

  Each test is shown to fail against a deliberately broken implementation,
  for example k off by one, or a re-sort by similarity. The failing output is
  recorded in the task's report.
- **Both suites, lint and build,** per AGENTS.md.
- **A smoke run** of `broad` with 5 questions against live NTER, with the
  output checked by hand.
- **Reproducibility.** Two consecutive runs on the same index build must give
  identical per-question outcomes. Any HNSW tie at a cutoff is reported, not
  hidden.

## No worse: the bar `retrieval-scope` must meet

These are absolute question counts on non-ambiguous questions, compared per
question against a baseline run **on the same corpus fingerprint and the same
index build**. If `retrieval-scope` rebuilds an index, the baseline is run
again on the new build before comparing, so that build noise isn't charged to
the change.

1. **`broad`:**
   - Overall document hit@10 loses at most 2 questions net.
   - No single question moves from a top-10 hit to a miss beyond 40.
   - Every lost question is listed with its before and after ranks.
2. **Per feature** (all five, including the small ones), `broad` document
   hit@10 loses at most 2 questions net in Bills or Regulatory, and at most 1
   in Parliamentary Questions, Industry or Budget.
3. **`feature` mode, the new behaviour:**
   - Per feature, document hit@10 is at least the same feature's `broad`
     baseline.
   - Every call returns the full `match_count` when the feature holds at
     least that many chunks. That catches the filter-after-HNSW failure on
     small features.
4. **`focused` and `focused-multi`:** identical per-question outcomes. The
   scoped SQL isn't meant to change. If it does, the change needs its own
   bar.
5. **Latency:**
   - Each mode's p95 is within 1.2× its baseline p95, plus 20 ms of jitter.
   - Any query slower than 2 s on the server is flagged. Signed-in users run
     under the `authenticated` role's 8 s statement timeout (executed:
     `pg_roles.rolconfig`), where the harness has 300 s.

## Boundaries

- **Always:**
  - Read-only against live NTER: `match_documents` and selects only.
  - Use stored vectors.
  - Record the set version, the fingerprint, the commit and the cost in every
    report.
- **Ask first:**
  - Adding a dependency (none is planned).
  - Generation and judging spend above $2 (expected well under $1).
  - Anything that needs a local corpus copy. That is designed in the
    `retrieval-scope` spec, not here.
- **Never:**
  - Write to the live database.
  - Commit corpus embeddings, corpus content or secrets. Results hold ids and
    ranks only.
  - Edit a frozen set.
  - Tune a change on the evaluation set without saying so in the report.

## Scope

The question set, its vectors and its builder; the harness with the `broad`,
`focused` and `focused-multi` modes; the baseline run and report. The
`feature` mode's runner can be written here, but it is exercised only when
`retrieval-scope` adds its SQL.

## Exclusions

- Changing retrieval: that is `retrieval-scope`, which also tests the
  handler's `document_ids` path and the model's feature choice.
- Judging answer quality.
- A local corpus copy: designed in `retrieval-scope` if needed.
- CI: the harness needs secrets.
- Page-level metrics. `ingestion-v2` rewrites chunks for new documents only,
  so this set, which uses existing documents, stays valid. Page accuracy gets
  its own set over the pilot documents. **`retrieval-scope` must be compared
  before any change re-indexes existing documents.**

## Review record

A fresh-context adversarial review of revision 1 (2026-09-30) raised 16
findings. All were accepted and addressed:

1. Gold was keyed on a hash the RPC doesn't return: it now uses
   `gold_chunk_id`.
2. The loose span-overlap rule was removed.
3. There was no corpus fingerprint: one is added, with an abort.
4. Query embeddings could vary: the vectors are now committed.
5. A false claim that the harness uses the same path as `research-chat` was
   corrected.
6. The bar didn't test the new behaviour: the `feature` bar was added and the
   small features are included.
7. Net totals could hide churn: comparisons are per question, with absolute
   counts and a same-build rule.
8. Latency bars contradicted the evidence: they are now relative to the
   baseline, with warm-up and a named network baseline.
9. The local replica design was unworkable: it is deferred to
   `retrieval-scope`.
10. Wrong style references: `load-desk-rows.mjs` is now cited.
11. Rule gaps: both suites, the status wording and the environment names are
    fixed.
12. `focused-multi` had edge cases: distractors are frozen, a skip rule
    added, and the quota cap stated.
13. The line schema was inconsistent: it now has a gold id array, a key
    looked up at build time, and the exact feature string.
14. Sampling was underspecified: it now cycles per document, uses the
    chunker's table rule, a defined normalisation, the ambiguity check, and
    the live model default.
15. The human check was weak: an independent judge, 38/40, and an owner
    18/20 were added.
16. Ranking could be re-sorted: row order and tie reporting are now
    specified.
